# Publish selected Competitions to a Postgres Published Store

*Relates to ADR 0011 (per-competition database / scoping), ADR 0023 (Viewer + published
serving DB), ADR 0021 (operator dashboard + command registry), ADR 0002 (raw cache →
SQLite), and ADR 0009 (concurrent-build lock).*

Every store this project holds is a local SQLite file: the authoritative `data/football.db`,
the scoped `data/<slug>.db` (ADR 0011), the serving `web/serve.db` (ADR 0023), the Live
Mirror (ADR 0020), the Refresh ledger (ADR 0018). We now want Liga MX (262) and Major
League Soccer (253) in a **remote Postgres** database, so tools and people that speak SQL
over the network — rather than a file on this box — can query them, and we want a re-run to
bring Postgres back in line with what we hold locally.

The credentials were added to `.env`. The naive read of the task is "concatenate
`data/liga-mx.db` and `data/major-league-soccer.db` and push the result". That is wrong, and
why it is wrong drives most of what follows.

**Decisions:**

- **One multi-Competition build, never a concatenation of scoped stores.** `Venue.id` is a
  **surrogate**, not a provider id: `parse._build_venues` enumerates the unique `(name, city)`
  pairs in sorted order and numbers them 1..N *per build* (the provider's own `venue.id` is
  null in ~32% of fixtures — see the `Venue` model). Two independently-scoped stores therefore
  both number their venues from 1, and **all 82** of `liga-mx.db`'s venue ids collide with a
  *different* stadium in `major-league-soccer.db` (id 1 is Estadio AKRON in one and Allianz
  Field in the other). Unioning the two files would relocate all 5,329 MLS fixtures to Mexican
  grounds. Instead `publish_pg` calls `parse.build(targets=…)` **once** over both Competitions'
  seasons, so venues are enumerated across the union and the ids are globally consistent by
  construction — the same property `football.db` has for all 39 Competitions. Teams and players
  were never at risk (both are provider ids); venues are the one surrogate in the dimension
  tables, and `Event.event_index` the other (below). The union is also strictly *better* than
  two stores side by side: the 153 players who appear in both leagues (Chucky Lozano, Héctor
  Herrera) collapse to one `player` row whose career spans both, which neither scoped DB can show.

- **Replace wholesale; never upsert.** "Update Postgres to what we have here" cannot mean
  `ON CONFLICT DO UPDATE`, because two keys are re-derived on every build: `Venue.id` (above —
  one new alphabetically-early stadium shifts *every* id) and `Event.event_index` (a row's
  position in the fixture's response array, documented as deterministic only "while the raw
  cache is stable"). An upsert would rewrite those ids' meanings under rows still pointing at
  the old numbering, and would never remove a row the provider has retracted. Wholesale
  replacement is the only sound refresh, and it matches how `parse.build` already treats
  `football.db` (drop and rebuild) and how `web.publish` treats `serve.db` (rebuild + swap).

- **Blue-green swap inside one transaction, moving tables rather than renaming `public`.**
  The load lands in a `football_next` staging schema; a single transaction then drops the ten
  published tables from `public`, `ALTER TABLE … SET SCHEMA public`s the staged ones over, and
  drops the staging schema. Postgres DDL is transactional, so a reader sees the previous store
  right up to `COMMIT` and the new one after — never a half-loaded table — and a crash mid-load
  rolls back to the previous store. This is `web.publish`'s `os.replace(tmp, serve.db)` discipline
  (ADR 0023) expressed in Postgres. We deliberately do **not** rename the `public` schema itself:
  on this Azure server `public` is owned by `azure_pg_admin` and carries PG 14's default `GRANT`s
  to role `PUBLIC`; promoting a staging schema into its place would yield a `public` owned by
  `gerardoma` with default ACLs, silently revoking other roles' access. Moving tables also keeps
  the blast radius to exactly the ten tables we publish — verified: an unrelated table in `public`
  survives a publish untouched.

- **Schema-identical to `football.db`, via `football.models`.** The Postgres DDL is generated by
  `SQLModel.metadata.create_all` against the same model definitions `parse.build` uses, not
  hand-transcribed — so the tables cannot drift from the SQLite stores, and `date`/`captain`
  land as real `timestamp`/`boolean` rather than SQLite's stringly-typed equivalents. All ten
  tables are copied in full (~498k rows: 286k squad entries, 123k events), not windowed the way
  `serve.db` is — the ask was "the same schema as liga-mx.db", which is a complete store, and
  the Viewer's rendering-driven window (ADR 0023) has no meaning for an open-ended SQL target.
  Tables land in `public`, so any query written against a scoped SQLite DB ports over verbatim.

- **The ESPN commentary store rides along, cloned in full and unscoped.** `narrated_match` /
  `commentary_line` (ADR 0026) are published into the same Postgres store and the same swap, so
  the whole thing turns over atomically. Two asymmetries are deliberate:
  - **Source.** The football tables are *re-parsed from the raw cache*; the commentary tables are
    *cloned from `data/commentary.db`*. They are not derivable from the API-Football cache at all
    — they come from a different provider and a pipeline that includes an LLM classifier — so a
    DB→DB copy (as `web.publish` does) is the only option. One command, two source models.
  - **Scope.** The `league_ids` argument scopes the football half and **not** the commentary half,
    which is always copied whole. A Narrated Match is ESPN's unit, keyed on ESPN's game id, and is
    *not Competition-scoped*: most have no Fixture at all because ESPN narrates competitions we do
    not collect (CONTEXT.md). "Publish only the commentary for these Competitions" would discard the
    majority of the store's own subject matter — of the current 4 Narrated Matches, one is Swedish
    Allsvenskan with no Fixture and two are World Cup.

  The accepted consequence is a property worth naming: **`narrated_match.fixture_id` may be non-null
  and still resolve to nothing**, because the Fixture's Competition was not published. Publishing the
  default pair today yields 1 bridge that resolves (Liga MX), 2 that dangle (World Cup — real in
  `football.db`, absent from a Liga MX + MLS store) and 1 with no link. This is not corruption: the
  bridge is optional and **never a foreign key** (CONTEXT.md: "a bridge, never the key"), exactly as
  `PlayerTeam.team_id` is not. Had it been made an FK, 2 of 4 rows would fail to load. Because a
  dangling bridge is *silent* in SQL — a join just returns nothing — `publish_pg` counts and prints
  the three outcomes after every run rather than leaving it to be discovered.

- **The commentary DDL is reused verbatim from `commentary.store.SCHEMA`.** Its SQLite DDL is valid
  Postgres unmodified — verified: `TEXT`/`INTEGER`/`REAL`, both `CHECK` constraints (Narration
  Coverage ∈ {narrative, events_only}; source ∈ {espn_keyevent, llm}) and all four indexes carry over,
  and `text`/`date` are legal column names in Postgres. So it is executed as-is rather than
  transcribed, giving the commentary half the same single-source-of-truth property `football.models`
  gives the other ten tables — including, for free, the absence of a `REFERENCES` on `fixture_id`.
  If `data/commentary.db` is absent the football half still publishes and any existing Postgres
  commentary tables are left untouched, rather than being silently emptied by the swap.

- **`FOOTBALL_DATABASE_URL`, not the bare `PG*` vars.** The project `.env` defines `PGHOST`/
  `PGUSER`/`PGDATABASE`/`PGPASSWORD` **twice** — once for `PGDATABASE=football` and again, on
  the same host and user, for `PGDATABASE=content_analysis` (the file is shared with another
  project; its header still reads "YouTube Trending V2"). Under any standard dotenv loader the
  *later* definition wins, so resolving the bare names would silently target the wrong database.
  A single explicitly-named URL sidesteps the duplication entirely and stays correct however the
  other project edits its own block. It is read by `config.load_pg_url()`, which reuses the
  hand-rolled first-wins `.env` reader `config.load_api_key()` already established — no
  python-dotenv dependency. (The password contains `%` and `!`, which must be percent-encoded:
  a raw `MTia100%s2026!!` makes any URL parser choke on `%s2` as a bad escape.)

- **Parameterized by league id, defaulting to the pair.** `python -m football.publish_pg` publishes
  Liga MX + MLS; ids can be passed explicitly, and `--all` publishes every tracked Competition.
  `parse.build` already accepts an arbitrary `targets` list, so generality is free, and it mirrors
  `football.scope`'s CLI. Season selection reuses `scope._cached_targets`, so a partially collected
  Competition publishes the seasons it has and reports the rest — cache-only, zero API, like scope.

- **The intermediate SQLite store is a throwaway in a temp dir.** Nothing reads it after the load,
  and putting it under `data/` would invite confusion with the scoped stores it deliberately is not.
  Its build lock lives in the temp dir too, so a publish never blocks — nor is blocked by — a
  `football.db` build (ADR 0009's lock is per `db_path`).

- **On the Console, a new `competitions` (multi-select) param kind — not the existing
  `competition` picker.** Registering the command in the ADR 0021 registry needed a widget the
  registry did not have. The existing `competition` kind is a *single* `<select>`, and reusing it
  here would be a live footgun: because a publish replaces the store wholesale, picking "Liga MX"
  would not *add* Liga MX, it would **delete MLS from Postgres**. The argument is a *set*, so the
  widget must be able to express a set. The new kind reuses the multi-select machinery the
  `fixture` kind already had (`build_argv` emits repeated positionals; selecting none emits
  nothing, so `publish_pg`'s own argparse default — the Liga MX + MLS pair — applies), and it is
  filled from the same `competition_options()` source, i.e. `competitions.json` (ADR 0019), never
  `football.db`. The destructive-by-omission semantics are spelled out in the param `help`, the
  command `detail` and the `example`, since the registry is the documented source of truth for
  what a command does (ADR 0021). This also makes `publish_pg` the first Publish-group command
  that never touches `football.db` — it derives from the raw cache — so it sets neither
  `builds_db` nor `network` (that flag means "spends API quota", which this does not, despite
  talking to a remote server).

- **`--all` stays a CLI convenience, unexposed on the Console.** The multi-select can already
  express "everything", the CLI rejects `--all` combined with ids (a form could submit both), and
  a dashboard button that silently launches a 39-Competition, ~388 MB publish is a footgun of a
  different kind. Nothing is lost: the terminal keeps calling `python -m` directly (ADR 0021).

## Considered Options

- **Concatenate the two existing scoped `.db` files, remapping venue ids with an offset.**
  Rejected: it hand-rolls id surgery that `parse.build` already does correctly for free, and it
  must rewrite every `fixture.venue_id` in lockstep or corrupt silently. It also cannot dedupe
  the stadiums (`Estadio Akron` already appears four times *within* `liga-mx.db` under spelling
  variants) or the 153 dual-league players, so the result would be strictly worse than a union build.

- **Drop the venue table and null `fixture.venue_id`.** Rejected: it sidesteps the collision by
  discarding 255 stadium rows and any home-venue analysis. The collision is trivially avoidable.

- **`TRUNCATE` + reload in one transaction.** Rejected in favour of the schema swap: it is equally
  atomic for readers, but `TRUNCATE` takes an `ACCESS EXCLUSIVE` lock, so readers *block* for the
  whole ~110s load instead of continuing to read the previous store. The staging swap holds that
  lock only for the final instant.

- **Point `parse.build` straight at Postgres (skip SQLite entirely).** Tempting — it takes an
  engine-able `db_path` — but rejected: the build's memory-batched commit/expunge discipline
  (ADR 0002/0009) is tuned for local SQLite, and it would hold a Postgres transaction open for the
  entire multi-minute parse to preserve the all-or-nothing swap. A local build then a bulk `COPY`
  keeps the network transaction to ~40s.

- **A `warehouse`/star-schema shape, or added indexes.** Rejected for now: a denormalised or
  dimensionally-modelled target forks the schema from `football.db` and breaks query portability,
  which is the main thing the shared model buys. Indexes beyond the model's primary keys are a
  reasonable future addition once real query patterns exist — deliberately not guessed at here.

- **Incremental sync of only the current Season (à la the nightly Refresh, ADR 0018).** Rejected as
  premature: the full publish takes ~110s end to end, which is well inside "just re-run it". Revisit
  if the Competition set grows enough that the re-parse dominates.
  *Revisited in ADR 0028:* once `--only` scoping (ADR 0018 amendment 2) made `refresh_pg` a frequent
  path, the re-parse *did* dominate, and a delta publish was added — `refresh_pg` now sends only
  new/re-healed Finals by default, with this wholesale build kept as the manual reset. That required
  making `Venue.id` stable across builds (a committed registry, `football/venues.json`), which
  amends the "surrogate re-derived per build" premise of the two decisions above.
